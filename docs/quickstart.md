# Quickstart

从零到一个能用的 STRATA 实例，再到**你自己测出它对你有没有用**。

预计时间：定义字典 20 分钟 · 首批条目 1–2 小时 · 判决层 1 小时 · 自测 半天。

> **先读一句警告。** 这个方法的**收益是假设，不是已验证的事实**。
> 下面的 §7 让你在自己的仓库上检验它 —— **请在投入大量时间之前先做 §1 和 §7**。
> 如果 §1 的测量说"不适用"，就停，别往下做。

---

## §0 先决条件

| 需要 | 为什么 |
|---|---|
一个 git 仓库，**约 30 个以上**源码文件 | 太小的仓库，索引成本大于收益 |
文件**会被修改** | 从不改动的代码不需要约定 |
有重复出现的同类文件 | 这是"面"的收益来源（§1 会量化）|
能跑一条检查命令 | 判决层需要它 |

**不需要**：任何特定的 Agent、任何 LLM API、任何依赖。所有脚本都是零依赖 Node。

---

## §1 先花 30 秒测量（必做）

不要先写索引。先测这个方法**对你是否可能有用**：

```bash
node scripts/measure.mjs --root /path/to/your/repo --depth 2
```

看 **κ** —— 与至少一个其他文件共享同一个面的文件比例。

| κ | 判定 | 你该做什么 |
|---|---|---|
**≥ 0.5** | 适用 | 继续 §2 |
**0.3 – 0.5** | 部分适用 | 继续，但结论只能限定在密集区域（§7 要求你报告范围）|
**< 0.3** | **不适用** | **停。** 直接跳到 §5（只做判决层），或换项目 |

### ⚠️ 重要：目录代理给出的 κ 只是**上界**

`measure.mjs` 默认用**目录结构**当面的代理。但"同一目录 ⇒ 同一个面"是构造上必然的，
所以这个 κ **系统性偏高**，不具区分力（实测同一仓库在 `--depth 1..4` 下 κ 恒在 0.94–0.99）。

**有意义的 κ 要用你自己的字典测**：

```bash
node scripts/measure.mjs --root /path/to/your/repo \
  --layers 'core,api,ui,infra' \
  --domains 'auth,billing,reporting'
```

脚本还会打印**顶层目录规模画像**，告诉你字典该切在哪一层：

```
   90  apps  ████████████████████████
   31  plugins  ████████················
  目录越大越值得为它细分「域」；只有一两个文件的目录是单文件面，收益为零。
```

同时它会算 **γ** —— 历史新增文件里"带来一个新面"的比例。
**γ 低 = 新文件大多落在已有的面上 = 面锚定有收益。**

## §2 定义字典（**顺序不能反**）

复制模板：

```bash
cp templates/instance-index.md docs/strata-index.md
```

**先填 §0**，也就是两个封闭枚举：

| 维度 | 含义 | 例子 | 规模建议 |
|---|---|---|---|
**A 层**（1 字符）| 架构角色 | `C`=core `R`=route `V`=view `D`=data `S`=script | **6–12 个** |
**B 域**（2 字符）| 业务域 | `AU`=auth `BL`=billing `RP`=reporting | **8–15 个** |

面数上界 = `|A| × |B|`。**两者都必须是有限枚举。**

> **为什么顺序不能反**：如果先写条目再回头补字典，你会不自觉地为每个文件造一个标签，
> 面就退化成文件，κ 变成 1.0，方法失效。
> **这是最常见的失败方式**，没有之一。

**怎么切分**：层按"改动它会不会波及其他层"来分；域按"业务上是否独立命名"来分。
不要按框架名分（`components`/`utils` 是位置，不是角色）。

---

## §3 写条目

每个文件一行：

```
path[layer·domain·importance·features·scale]: F:role | R:related | A:exports | S:notes
```

**只写"读代码看不出来"的东西。** 不要复述函数签名 —— 那是冗余的 token。

**`S`（notes）是全文最有价值的部分**，它承载的是：

| 该写 | 不该写 |
|---|---|
为什么这么设计（取舍）| 函数签名 |
什么改动会踩坑 | 逐行注释翻译 |
和哪些文件必须一起改 | "这个文件定义了 X 类" |
隐含的不变量 | 能从代码看出的任何东西 |

**重要性（C 维）用 6 级非均匀制**：`9 / 8 / 7 / 5 / 3 / 1`。
不是平均分 —— 核心文件之间要保留细粒度区分，外围文件合并压缩。
`C` 可以理解成**给这个文件的 token 预算**。

## §4 把约束挂到面上（核心步骤）

这一步是 STRATA 区别于普通索引的地方：**约束的适用范围写成面，不写成文件路径**。

```yaml
constraints:
  - id: no-shell-exec
    scope: scripts/*            # ← 面：scripts/ 下的一切
    why: 防止命令注入
    check: "! grep -rn 'execSync\\|spawnSync' src/scripts"

  - id: no-backtick-in-template-comment
    scope: lib/render             # ← 面
    why: 模板字面量内的注释若含反引号会提前结束模板，报错位置远离真因
    check: "node tools/check-parse.mjs src/lib/render"
```

**自检**：随便想一个你**明天可能要新建的文件**，问自己：

> 它落在哪个面上？那个面上已有的约束**自动适用**于它吗？

如果答案是"是"，锚定就生效了 —— 你不需要为它写任何新规则。
如果答案是"不是，我得为它写新规则"，说明这个面切得不对，或者它确实是个新面。

**这一步的价值可以量化**：`measure.mjs` 的 γ 就是这个"要不要写新规则"的比例。

## §5 判决层：让约束可执行

**这是最可能真正改变 Agent 行为的一层。** 参照物是别人的实证结论：

> *"cheap signals may prioritize work, but only an executable checker can
> establish the property being claimed"* — [arXiv:2610.04779](https://arxiv.org/abs/2610.04779)

也就是说：**散文形式的规则，和可执行形式的规则，效力不同**。
（这一条在本仓库的起源案例里有观察性支持：一条已写入文档的禁令在 26 天内复发 21 次，
直到出现可执行检查器。**但那是 n=1 的观察，不是因果证据。**）

约定：

| 退出码 | 含义 |
|---|---|
**0** | 通过 |
**1** | 失败（附上违反的约束 id 与位置）|
**2** | **无法判定** —— 诚实优于假装通过 |

**为什么必须有 2**：很多规则不可判定（"命名是否清晰"）。
强迫给出 pass/fail 只会产出假信号。把"不知道"显式暴露出来，比假装知道更有用。

聚合入口（让 Agent 一条命令能跑）：

```bash
npm run strata:check      # 或 make check / pnpm check / 你的习惯
```

**输出必须可操作**：犯规的文件、行号、约束 id。Agent 读得懂才改得动。

**没有判决层会怎样**：你只剩索引。索引对"去哪找"有帮助，但对"别再犯这个错"几乎无效。

## §6 让 Agent 用上它

三种接入方式，按侵入性递增：

| 方式 | 做法 | 适合 |
|---|---|---|
**约定文件** | 在你的 `AGENTS.md` / `CLAUDE.md` 里写"改代码前先读 `docs/strata-index.md`" | 最快 |
**任务模板** | 每次派活时把相关条目 + `strata:check` 一起给 Agent | 可控 |
**自动化** | 用 `scripts/bench.mjs` 的 `strata` 条件构造上下文 | 做实验时 |

**关键提醒**：把你的 `strata:check` 命令明确写进约定文件。
它存在的意义就是"**别的 Agent 会话也会跑它**"。

## §7 自测：在你自己的仓库上测出提升比（**核心**）

这是本文档最重要的部分。**一个无法自证有效的方法，只能要求你凭信念采纳 —— 那不够。**

### 7.1 三条件设计

同一批任务，在三种上下文条件下各跑一遍：

| 条件 | 给 Agent 什么 |
|---|---|
**C1 `no-context`** | 只给任务描述 |
**C2 `raw-files`** | 任务相关文件的**源码** |
**C3 `strata`** | STRATA **索引与约束**（不给源码）|

> **为什么必须有 C2。** 如果只比 C1 与 C3，你测的是"多给上下文有没有用"，
> 不是"STRATA 有没有用"。
> **C3 相对 C2 的提升，才是 STRATA 的贡献。** 若 C3 ≈ C2，说明提升来自上下文数量，
> 而不是结构化 —— **这个结论也必须如实报告。**

### 7.2 生成任务

用仓库自己的历史提交当题目：

```bash
node scripts/bench.mjs init \
  --repo /path/to/your/repo \
  --out bench/tasks \
  --limit 10 \
  --verify-cmd 'npm test -- --run'      # 判定命令，见下
```

`prompt` = 提交信息（自动去掉 `fix(x):` 前缀）；`baseRef` = 该提交的父提交。

**判定命令必须满足两个条件**：

| 在 baseRef 上 | 在真实提交上 |
|---|---|
**失败** | **通过** |

在生成后亲手验一个任务，确认这两点。**任务质量决定实验质量** ——
垃圾任务会给出垃圾的"提升比"，而且看不出是任务的问题。

### 7.3 跑

```bash
node scripts/bench.mjs run \
  --tasks bench/tasks \
  --out bench/results \
  --conditions no-context,raw-files,strata \
  --repeat 3 \
  --agent-cmd 'your-agent --prompt-file {prompt} --cwd {cwd}'
```

| 要点 | 说明 |
|---|---|
`--repeat 3` | Agent 有随机性，单次运行说明不了问题 |
`--agent-cmd` | 换成你自己的 Agent 命令；**省略则进入手动模式**（工具打印 prompt，你手动跑）|
判定脚本 | **不会进 prompt** —— Agent 看不到它。否则测的是"能不能猜中测试" |
工作副本 | 每个 run 用独立 `git worktree`，不污染你的仓库 |

### 7.4 读报告

```bash
node scripts/bench.mjs report --results bench/results
```

输出形如：

```
  条件            运行  通过   成功率
  no-context       30    12    40.0%  ████████████··················
                                   95% CI [24.6%, 57.7%]
  raw-files        30    19    63.3%  ███████████████████···········
                                   95% CI [45.5%, 77.9%]
  strata           30    25    83.3%  █████████████████████████·····
                                   95% CI [66.4%, 92.7%]

── 提升 ──
  STRATA vs 无上下文 : +43.3 个百分点   提升比 2.08×
  STRATA vs 原始源码 : +20.0 个百分点   提升比 1.32×
```

**怎么读**：

| 观察 | 结论 |
|---|---|
C3 的 CI 与 C1、C2 **都不重叠**，且明显更高 | 支持 STRATA 有效 |
C3 ≈ C2，两者都高于 C1 | **提升来自上下文量，不是结构** —— 必须如实报告 |
C3 与 C1 无差异 | 在你这个仓库上**没有效果**，这是有价值的负结果 |
CI 全部重叠 | **样本量不够**，加大 `--repeat` 或增加任务 |

### 7.5 报告结论时必须写的限制

工具会自动打印这些，请一并写进你的结论：

| 限制 | 为什么 |
|---|---|
**样本量** | 小样本的差异可能是噪声 —— 看 95% CI 是否重叠 |
**预训练泄漏** | 公开仓库的历史提交可能被模型见过；私有仓库或未公开分支可缓解 |
**上下文长度不同** | 三条件给的内容量不同，这本身影响结果（C2 即为控制它而设）|
**Agent 随机性** | 单次运行不能说明问题 |
**判定命令的效度** | 你的 `verifyCmd` 是否真的等价于"任务做对了"？它可能过严或过松 |

**必须报告 CI，不能只报点估计。** 只报"提升了 20 个百分点"而不给区间，
是在用一个可能毫无意义的数字下结论。

## §8 维护

| 时机 | 动作 |
|---|---|
新增文件 | 补一条条目；**检查是否需要新约束** —— 理想情况是不需要（这正说明锚定生效）|
改了公开接口 | 更新该条目的 `A` 与相关条目的 `R` |
踩到新坑 | §4 加一行，**并给它一个可执行检查形态**（写不出来 ≙ 它大概率不会生效）|
文件重要性变了 | 改 `C` 值 —— 它是 token 预算 |
每季度 | 重跑 `measure.mjs`，看 κ 与 γ 是否漂移 |

**索引过期比没有索引更危险** —— 它看起来权威。所以：
**让 `strata:check` 顺便校验索引完整性**（新增文件是否都有条目），把"记得更新"变成机械检查。

---

## 回到原点

如果你做完 §7 发现**效果不显著**，请如实报告。负结果同样有价值 ——
它说明"结构化上下文"在**你的项目类型**上不是瓶颈，瓶颈可能在别处（任务拆分、判定质量、模型能力）。

这正是本方法一开始就承认"未验证"的意义：**它是待检验的假设，你是检验者之一。**
